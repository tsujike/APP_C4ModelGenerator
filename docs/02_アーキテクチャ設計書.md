# アーキテクチャ設計書 — Mermarium(マーマリウム)

版 1.0 / 2026-07-18。要件は `docs/01_要件定義書.md` を正とする。本書は「どう作るか」を定める。

## 1. 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| ビルド | Vite | 静的成果物のみ。設定が薄い |
| 言語 | TypeScript (strict) | モデル/射影ロジックの型安全性が品質に直結 |
| レイアウト | elkjs (`org.eclipse.elk` のJS移植) | 階層(入れ子)レイアウトとエッジルーティングを標準サポート(Excalidrawは自動レイアウトを持たないため必須) |
| 描画キャンバス | Excalidraw(`@excalidraw/excalidraw`、OSS) | ホワイトボードのルック&フィール、パン/ズーム/エクスポート/閲覧専用モードが内蔵。要素は `ExcalidrawElement[]` として全てプログラム生成し、`viewModeEnabled` で閲覧専用にする |
| カメラ制御 | Excalidraw の `onChange`(appState.zoom/scroll 監視)+ `updateScene`(要素・scrollX/scrollY・zoom の適用) | アンカー保存(FR-5.4)を updateScene によるシーン差し替え+カメラ補正で実現する。**成立性は T2-0b スパイクで最初に検証し、不成立なら自作SVGレンダラー(§12 付録)へ回帰する** |
| Reactランタイム | react / react-dom(Excalidraw のホストとしてのみ) | Excalidraw が React コンポーネントであるため。アプリ自体のUI(ツールバー・エディタ・パネル)には React を使わない |
| エディタ | Phase 3までは `<textarea>`、Phase 4で CodeMirror 6 | まず本質(ズーム)に投資する |
| テスト | vitest | Vite統合 |
| UIフレームワーク | アプリUIには使わない(Vanilla TS + DOM) | 画面が単純で状態源も1つ。React は Excalidraw ホストに閉じ込める |

## 3. データフロー(単方向)

```
テキスト変更 → parser(AST + issues) → model.build(C4Model + issues)
  → layout(レベル別 LayoutResult ×最大4、キャッシュ) → toExcalidraw(現レベルの要素群)
  → excalidrawAPI.updateScene({elements})
Excalidraw onChange(wheel/drag はExcalidrawが処理) → zoom/scroll 監視 → レベル判定
  → (切替時) 次レベルの要素群+アンカー補正済み scroll を updateScene で同時適用
```

- 解析〜レイアウトはテキスト変更時のみ実行。ズーム操作では再実行しない(キャッシュ済みLayoutResultを変換・適用するだけ。ExcalidrawElement[] もレベル別にキャッシュしてよい)。
- レベル別レイアウトは遅延生成でよい(初回にそのレベルが表示された時に計算しキャッシュ。テキスト変更で全キャッシュ破棄)。

## 4. 統一モデル

```ts
// model/types.ts
export type NodeKind =
  | 'person' | 'system' | 'container' | 'component' | 'class'
  | 'boundary';                       // Enterprise_Boundary等の純粋なグループ
export type NodeVariant = 'default' | 'db' | 'queue';
// L1〜L4=Context/Containers/Components/Code(C4モデル自体の4層)。
// L5〜L8はMermaidモード専用の追加レベル(C4モデル自体は4層で定義されるため、C4モードでは使わない。§13)。
export type Level = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8;

export interface C4Node {
  alias: string;          // ソース内で一意。グローバル名前空間
  label: string;
  kind: NodeKind;
  variant: NodeVariant;
  external: boolean;      // *_Ext
  technology?: string;
  description?: string;
  level: Level;           // この要素が「登場する」レベル
  children: C4Node[];     // 下位レベル要素(System→Container→Component→Class)
  parent?: C4Node;
  members?: { fields: string[]; methods: string[] }; // kind==='class' のみ
  sourceLine: number;
}

export interface C4Edge {
  from: string;           // alias参照
  to: string;
  label?: string;
  technology?: string;
  bidirectional: boolean;
  declaredLevel: Level;   // 宣言されたブロックのレベル
  sourceLine: number;
}

export interface C4Model {
  roots: C4Node[];        // L1要素(Person/System/外部システム)
  byAlias: Map<string, C4Node>;
  edges: C4Edge[];
}

// 注: ParseIssue 型は parser/types.ts で定義し、model 側はそれを import して使う。
// export interface ParseIssue { severity: 'error' | 'warning'; line: number; message: string; }
```

### 階層の構築規則
- `C4Context` ブロックの要素が `roots` になる。ソース中に必ず1つ(0個なら error、2個目以降は warning で無視)。
- `C4Container` ブロックは、直下の `System_Boundary(alias, ...)` の alias が Context の System と一致することで結び付く。ブロック内の Container 群がその System の children になる。Boundary 外に書かれた要素は warning で無視。
- `C4Component` ブロックは同様に `Container_Boundary(alias, ...)` で Container に結び付く。
- `classDiagram` ブロックは直前行の指令コメント `%% code-of: <componentAlias>` で Component に結び付く。指令が無い/未解決なら該当ブロック全体を warning で無視。
- `Enterprise_Boundary` は kind=boundary のノードとして `roots` に入り、囲まれた Person/System はその children になる(囲まれていない要素は従来どおり roots 直下)。boundary はあくまで視覚グループであり、level は 1、全レベルで常に破線枠として描画され、エッジ射影(§6)の射影先には**ならない**(祖先探索時に読み飛ばす)。
- alias 重複はグローバルに error(後勝ちせず初出を採用)。
- Boundary の alias が未解決の場合、そのブロックは warning を出して無視する(FR-2.3: 描画は継続)。

## 5. 入力DSL仕様(Mermaid C4 サブセット+拡張)

### 5.1 ブロック分割
行頭が `C4Context` / `C4Container` / `C4Component` / `classDiagram` の行で新ブロック開始。ブロックはファイル終端または次のブロック開始行まで。インデントは自由。空行・`%%` コメント行は無視(ただし `%% code-of:` は指令として解釈)。

### 5.2 C4系ブロックの対応文法

引数は `(` `)` 内のカンマ区切り。各引数は `"..."` 引用符付き文字列または裸の識別子。引用符内のカンマは区切りとみなさない。`$tag=...` 形式の名前付き引数は無視(warning不要)。

| 文 | 解釈 |
|---|---|
| `Person(alias, label, ?descr)` / `Person_Ext(...)` | kind=person, external有無 |
| `System(alias, label, ?descr)` / `System_Ext` | kind=system |
| `SystemDb(...)` / `SystemDb_Ext` / `SystemQueue(...)` / `SystemQueue_Ext` | variant=db/queue |
| `Container(alias, label, ?tech, ?descr)` / `Container_Ext` / `ContainerDb` / `ContainerQueue` | kind=container |
| `Component(alias, label, ?tech, ?descr)` / `Component_Ext` / `ComponentDb` / `ComponentQueue` | kind=component |
| `System_Boundary(alias, label)` `{`〜`}` | C4Containerブロック内: 親Systemへの結び付け |
| `Container_Boundary(alias, label)` `{`〜`}` | C4Componentブロック内: 親Containerへの結び付け |
| `Enterprise_Boundary(alias, label)` `{`〜`}` | Contextブロック内の視覚グループ(kind=boundary) |
| `Rel(from, to, label, ?tech)` | エッジ |
| `BiRel(from, to, label, ?tech)` | bidirectional=true |
| `Rel_U/Rel_D/Rel_L/Rel_R/Rel_Up/...(方向付きRel)` | `Rel` と同義に解釈(方向ヒントは無視、warningなし) |
| `title ...` | 無視(warningなし) |
| `UpdateRelStyle/UpdateElementStyle/UpdateLayoutConfig` | 無視(warningなし) |
| 上記以外の非空行 | warning「未対応の文」+ 行無視 |

- Boundaryの `{` `}` は同一行末尾/単独行のどちらも許容する。閉じ忘れはブロック終端で暗黙クローズ+warning。
- Rel の from/to は**グローバルなalias**を参照する。異なるレベルの要素同士のエッジも合法(例: L2ブロック内で Person→Container)。未解決aliasのRelは error でその行のみ無視。

### 5.3 classDiagram サブセット

| 文 | 解釈 |
|---|---|
| `class Name { ... }`(複数行ボディ) | kind=class ノード。ボディの各行: `+x()` `-y(...)` など `(`を含む行は method、それ以外は field |
| `class Name` | 空のクラス |
| `A --> B : label` / `A --|> B` / `A *-- B` / `A o-- B` / `A ..> B` | エッジ(declaredLevel=4)。矢印種別はMVPでは描画上すべて実線矢印+継承(`--|>`)のみ白抜き三角 |
| その他(`<<interface>>`等) | warning無しで無視 |

## 6. エッジ射影・集約アルゴリズム(FR-5.8)

表示レベル n(1..4)で描画するとき:

1. **可視ノード集合 V(n)** を決める: 深さ ≤ n の全ノード。ただし子を持つノードで子が可視のものは「境界(展開枠)」= §7.2 の Boundary スタイル(破線・塗りなし・左上ラベル)で描画し、自身の種別色では塗らない。子を持たない/子が定義されていないノードは葉として種別色の箱で描画する(FR-5.7)。
2. 各エッジ e について、`from` / `to` それぞれを **可視な最深祖先**(自身が可視なら自身)へ射影する。
3. 射影後に from==to(同一の折りたたみノード内部の関係)となったエッジは捨てる。射影後の端点が展開中の境界ノード自身になるエッジは、境界枠に接続して描画する。
4. **重複集約**: 射影後の (from, to, bidirectional) が同じエッジ群は1本に集約する。代表ラベルは「declaredLevel が表示レベル n に最も近い(|declaredLevel−n| 最小、同値なら浅い方)エッジ」のもの。集約数が2以上ならラベル末尾に ` (+k)` を付ける(k=集約された他エッジ数)。

これは純関数 `project(model, level): ProjectedGraph` として実装し、ユニットテストの主対象とする。

## 7. レイアウトと描画

### 7.1 レイアウト(elkjs)
- レベル n の描画グラフ: 可視ノード(境界は elk の子付きノード)+射影済みエッジを elk グラフに変換。`elk.algorithm: layered`、`elk.hierarchyHandling: INCLUDE_CHILDREN`、方向 `DOWN`、spacing は constants.ts で管理。
- 葉ノード寸法はテキストから見積もる(ラベル幅×フォントメトリクス近似+説明文折返し行数)。厳密測定は不要、`ctx.measureText` 使用可。
- L4 のクラス図もこの仕組みに乗せる(Component境界の中にクラス箱)。
- 出力 `LayoutResult`: ノードごとの絶対座標/寸法、エッジごとの折れ線経路とラベル位置。世界座標系はレベルごとに独立でよい(§8のアンカー保存で橋渡しする)。

### 7.2 C4スタイル(theme.ts)— Excalidraw要素へのマッピング

1つの図形ノード=複数の ExcalidrawElement を同一 `groupIds` で束ねたグループとして生成する。id はレベルとaliasから決定的に生成する(例: `L2:api:box`)— アンカー特定(§8.3)や差分デバッグに使うため。

| 要素 | Excalidraw表現 | 塗り(backgroundColor, fillStyle: solid) | 文字 |
|---|---|---|---|
| Person | 角丸rectangle+頭部ellipseのグループ | #08427B(Ext: #686868) | 白 |
| System | 角丸rectangle | #1168BD(Ext: #999999) | 白 |
| Container | 角丸rectangle | #438DD5(Ext: #999999) | 白 |
| Component | 角丸rectangle | #85BBF0(Ext: #999999) | #000 |
| Db variant | rectangle+上部ellipseでシリンダー近似(グループ) | 同上の各色 | 同上 |
| Queue variant | 横長の角丸rectangle(両端ellipse省略可) | 同上の各色 | 同上 |
| Class | rectangle 3枚(名前/フィールド/メソッド)のグループ | #FFFFFF 枠#333 | #000 |
| Boundary(展開枠) | strokeStyle: dashed の rectangle+左上text | 塗りなし | #444 |
| エッジ | arrow 要素+ラベルtext(boundElement) | 線#707070 | #333 |

- 手描き風パラメータ: `roughness: 1`(既定)、`strokeWidth: 1`。ホワイトボードらしさはExcalidrawの標準描画に任せ、独自スタイルを盛らない。
- ノード内テキスト: text要素で 1行目 label(太字相当はfontSize差で表現)、2行目 `[technology]`(あれば)、3行目以降 description 折返し(最大3行、超過は…)。改行はテキスト整形時に自前で入れる。
- エッジ経路: elkjsの折れ線経路を arrow の `points` に渡す。矢印終端は `endArrowhead: 'arrow'`、継承(L4の `--|>`)のみ `'triangle'`。

## 8. カメラ・セマンティックズーム

### 8.1 カメラ
- パン/ズーム操作(wheel・drag・ピンチ)は**Excalidrawが処理する**。自前実装しない。
- アプリは `onChange(elements, appState)` で `appState.zoom.value` / `scrollX` / `scrollY` を監視し、正規化ズーム値 s = `zoom.value / z0` を得る。**z0 は起動時に L2 レイアウトを Fit 表示(`scrollToContent(…, { fitToViewport: true })`)した直後の zoom.value** とし、以後固定する(テキスト変更でも再計算しない=閾値の体感が安定)。
- カメラのプログラム制御(レベル切替時・Fitボタン)は `updateScene({ appState: { scrollX, scrollY, zoom } })` で行う。この制御が現行バージョンで成立することを **T2-0b スパイク**で最初に確認する(不成立時は§12へ回帰)。
- 図の編集を防ぐため `viewModeEnabled: true` で運用する(FR: 編集はテキスト経由のみ)。

### 8.2 レベル判定(lod.ts)
- AUTOモード: FR-5.1 の閾値表に対する**非対称ヒステリシス**を純関数 `nextLevel(current, s, maxLevel): Level` で実装する。`maxLevel` は上昇方向の上限レベルであり、呼び出し側がモードに応じて渡す(C4モード=4、Mermaidモード=8。FR-7.9)。
  - 上昇方向(ズームイン): s が上側閾値に達したら即遷移(例: s ≥ 1.5 で L2→L3)。ただし現在レベルが `maxLevel` に達している場合はそれ以上遷移しない。C4モードは `maxLevel=4` を渡すため、s が 3.0 を超えて上昇し続けてもL4で頭打ちになり、既存の挙動(v1.0時点の3閾値のみの判定)と完全に同一のまま保たれる。
  - 下降方向(ズームアウト): s が「現在レベルの下側閾値 × 0.9」を下回ったときに遷移(例: L3 中は s < 1.35 で L2 へ。s=1.4 では L3 維持)。
  - つまりヒステリシス幅10%は下降側にのみ適用する。この規則が正であり、FR-5.2 の「±10%」はこの意味に読み替える。
- 閾値(`LOD_ZOOM_THRESHOLDS`、`constants.ts`)は先頭3値([0.75, 1.5, 3.0])がFR-5.1の既存受入基準・既存lodテストの直接参照対象であるため変更しない。L5〜L8向けに4値([4.5, 6.75, 10.0, 15.0])を末尾に追加した。

  | 描画レベル | s の範囲(既定) | 対応モード |
  |---|---|---|
  | L1 | s < 0.75 | 両方 |
  | L2 | 0.75 ≤ s < 1.5 | 両方 |
  | L3 | 1.5 ≤ s < 3.0 | 両方 |
  | L4 | 3.0 ≤ s(C4モードはここで頭打ち) / 3.0 ≤ s < 4.5(Mermaidモード) | 両方 |
  | L5 | 4.5 ≤ s < 6.75 | Mermaidモードのみ |
  | L6 | 6.75 ≤ s < 10.0 | Mermaidモードのみ |
  | L7 | 10.0 ≤ s < 15.0 | Mermaidモードのみ |
  | L8 | 15.0 ≤ s | Mermaidモードのみ |

- 手動固定モード: 判定をバイパス。

### 8.3 レベル切替とアンカー保存(FR-5.4)
1. 切替直前、アンカー画面座標 p(直近のポインタ位置。無ければビューポート中心)の直下にある最前面ノード a を旧レベルのレイアウトから求める(無ければ最近傍ノード)。画面↔世界座標の変換は Excalidraw の規約 `screen = (world + scroll) × zoom` に従う(要素idの決定的命名 §7.2 を使い、LayoutResult側の座標で判定してよい)。
2. 新レベルのレイアウトで a に対応するノード a' を求める: a が新レベルで展開されるなら a' = a の境界枠、a が新レベルに存在しない(折りたたまれる)なら a' = a の可視祖先。
3. 「a' の中心が画面座標 p に来て、かつ現在の zoom を維持する」scrollX/scrollY を計算し、**新レベルの elements と併せて1回の `updateScene` で適用する**(要素とカメラを同時に切り替え、中間状態を見せない)。
4. 遷移は即時差し替えとする。クロスフェードは実装しない(Excalidrawはcanvas描画のためレイヤ合成による安価なフェードができない。FR-5.3参照)。切替直後の1操作が失われないよう、onChange 監視は差し替え後も継続する。
5. **モード切替時の上限追従**: `LevelController` は `maxLevel`(C4モード=4 / Mermaidモード=8)を状態(`LevelControllerState.maxLevel`)として保持し、`updateModel(model, levelData, maxLevel)` の呼び出しのたびに更新を受け取る。テキスト編集によりモードが切り替わり、現在の `level`(固定中は `levelLock`)が新しい `maxLevel` を超えた場合は、カメラ(scroll/zoom)には触れずに表示レベルのみ `maxLevel` へ丸める(例: Mermaidモードで L7 を表示中にマーカーを全て消してC4モードへ戻ると、自動的に L4 へ丸められる)。

## 11. 主要な設計判断の記録

- **描画キャンバスに Excalidraw 採用(2026-07-18 変更)**: 当初はアンカー保存の完全制御のため自作SVGレンダラーを採用していたが、ユーザー指示により OSS の Excalidraw に変更。API調査の結果、`updateScene` による要素+scroll/zoom の同時適用でアンカー保存が実装可能と判断した。ホワイトボードのルック&フィール・パン/ズーム・エクスポート・閲覧専用モードが内蔵で得られる。代償: React ホスト同梱、クロスフェード廃止(即時差し替え)、DB/人物形状は基本図形の合成で近似。**前提が崩れた場合(T2-0b スパイク不成立)は§12の自作SVG案へ回帰する。**
- **Mermaid.js に描画させる方式は不採用**: レベル間の位置連続性(アンカー保存)を制御できないため(当初判断のまま)。**post-v1.0のMermaidモード(§13)でもこの判断は変えていない**: Mermaidにはレイアウト計算のみを行わせ、その結果をExcalidraw要素へ変換して描く。アンカー保存を捨てているのはMermaidモードだけであり、そこでは対応ノードの概念自体が無いためそもそも成立しない(C4モードのアンカー保存は不変)。
- **レベル=グローバル切替(ノード個別LODではない)**: ノードごとに展開状態を持つ地図型LODはレイアウト再計算が頻発し複雑度が跳ね上がる。まず全体切替+アンカー保存で核体験を成立させる。個別LODは将来拡張(スコープ外)。
- **レベルごとに独立レイアウト+キャッシュ**: 入れ子共通座標系で全レベルを1レイアウトに押し込む案は、L4まで含めるとL1の箱が巨大化し破綻するため不採用。
- **classDiagram + `%% code-of:` 指令**: MermaidにCode層の標準記法が無いため、既存記法(classDiagram)に最小の拡張(指令コメント)で対応。

## 12. 付録 — フォールバック案: 自作SVGレンダラー(初版設計)

T2-0b スパイクで Excalidraw のカメラ制御(updateScene による scroll/zoom 適用、onChange での zoom 監視)が成立しない場合に採用する当初案の要点。判断は指揮者が行う。

- 描画: `render/render.ts` が LayoutResult→SVG DOM を直接生成(§7.2の形状・配色は同じ意味論でSVGに描く)。
- カメラ: SVG `viewBox {x,y,w,h}` を自前管理。wheel はカーソル位置固定ズーム、drag はviewBox平行移動。s = 画面px幅/viewBox幅 を L2 Fit 基準で正規化。
- 遷移: 旧SVGレイヤをフェードアウト・新レイヤをフェードイン(200ms、opacityのみ)でクロスフェード可能。
- §8.2(レベル判定)・§8.3(アンカー保存の手順1–2)・§6(射影)・§7.1(レイアウト)はそのまま流用できる。影響はレンダラーとカメラ層に閉じる。

## 13. Mermaidモード(post-v1.0、FR-7)

C4モードと**排他**の任意機能。既存パイプライン(`parser → model → layout → render`)には一切手を入れず、`main.ts` の1箇所のモード分岐で経路そのものを差し替える。**L5〜L8(FR-7.9)はMermaidモード専用の追加レベルであり、C4モードはL1〜L4のまま変わらない**(§4のLevel型、§8.2の閾値表を参照)。

### 13.1 経路

```
source ──isMermaidModeSource()?──┬─ false → 既存C4経路: buildModel → buildLevelData(layout+render)
                                 └─ true  → splitMermaidLevels → convertMermaidToElements(レベルごと)
                                                     ↓
                                       Map<Level, LevelData> ──→ LevelController(既存のまま)
```

両経路の出力は同じ `Map<Level, LevelData>` に収束する。`LevelData.elements` の型 `ExcalidrawElementSkeleton[]` が、`render/toExcalidraw.ts` の出力と `parseMermaidToExcalidraw` の戻り値で一致しているため、レベル切替機構(§8.3)をそのまま再利用できる。

### 13.2 モジュールと責務

| モジュール | 責務 | 備考 |
|---|---|---|
| `parser/mermaidLevels.ts` | `%%L1`〜`%%L8` の分割・警告生成、およびマーカー無しMermaidの検出(FR-7.8)。純関数、DOM非依存 | Mermaid本体は読み込まない(§2の依存方向を守る) |
| `excal/mermaid.ts` | `parseMermaidToExcalidraw` の薄いラッパ | Mermaidは一時DOMを作るためブラウザ専用依存として `excal/` に閉じる(vitestがnode環境で読み込まないようにするため) |
| `samples/mermaid-levels.ts` | 組込サンプル3「Mermaid(レベル別)」 | L1〜L7を登録し、L8を意図的に未登録にしてFR-7.4を通常操作で確認できるようにしてある |

### 13.3 既存モジュールへの変更点(最小)

- `LevelData.layout` を必須→**任意**にした。Mermaidモードでは統一モデルが無く対応ノード表(`model.byAlias`)を作れないため、`applySwitchElements` は両レベルの `layout` が揃っている時のみアンカー保存を行い、それ以外は要素だけ差し替える(カメラ据え置き)。
- `LevelData.files`(`BinaryFiles`)を追加。画像フォールバック時のimage要素は `fileId` で参照するだけなので、`host` 側で `api.addFiles()` を呼ばないと表示されない。`ExcalidrawHost.updateElements` / `applyLevelSwitch` / `mountExcalidraw` が `files` を受け取る。
- 同じ理由で、エクスポート経路(`ExcalidrawHost.exportSvgString` / `exportPngBlob` → `ui/exporter.ts` → `main.ts`)にも `files` を通す。v1.0では `files: null` 固定だったため、そのままでは書き出したSVG/PNGから画像フォールバックの図が丸ごと欠ける。
- 未登録レベルはキーを省略せず `{ elements: [] }` を入れる(「8レベル分が必ず揃っている」というLevelControllerの前提を崩さないため)。
- C4モードでも同じ前提を保つため、`main.ts` は L1〜L4 のみを実際に射影/レイアウト計算し、L5〜L8には空の `LevelData`(`{ elements: [] }`)を入れて `Map<Level, LevelData>` を8レベル分揃える(C4モデルにはL5以降の意味論が無いため、そもそも計算する対象が存在しない。無駄なelkjs計算を避けつつLevelControllerの「全レベル分そろっている」契約はモードによらず共通に保つ)。
- `main.ts` に `pickInitialLevel` を追加。Mermaidモードでは既定初期レベル(L2)が空になり得るため、要素を持つ最初のレベルから開始する(空表示でFitするとz0が不定になる既知の問題を避ける)。
- `main.ts` の `buildFromSource` のC4モード側に、`detectMarkerlessMermaidLine`(FR-7.8)の結果に応じた案内issueの追加を1箇所だけ入れた。検出は `parser/mermaidLevels.ts` の純関数に置き、issueの生成のみを `main.ts` が行う。**`model/build.ts`(C4解析本体)は依然として無変更**で、C4モードの解析結果そのものは変わらない(issuesへの追記だけ)。

### 13.4 変換の実測結果(@excalidraw/mermaid-to-excalidraw@2.2.2 + mermaid@11)

| 入力 | 結果 |
|---|---|
| `flowchart`(subgraph無し) | rectangle/arrow等のネイティブ要素へ変換 |
| `sequenceDiagram` | ネイティブ要素へ変換 |
| `flowchart`(subgraph有り) | image要素1個+files へフォールバック(ライブラリ側が `SubGraph element not found` をconsoleに出す) |

### 13.5 軸モード宣言とレベル名(Issue #1/#2/#5)

- `%% MODE:` の解析は `parser/mermaidLevels.ts` の `splitMermaidLevels` 内で行い、`MermaidLevelsResult.axisMode: AxisMode`(FR-7.10)として返す。解析・警告生成ともに純関数の内側に閉じており、`parser/` はDOM非依存のままである。
- `main.ts` は `BuildResult.axisMode?: AxisMode` としてこれを受け取る(C4モードには軸モードの宣言が無いため`exactOptionalPropertyTypes`によりキーごと省略する)。`renderAxisMode` はツールバーの `#axis-mode` 要素の `textContent` を書き換えるだけで、他の状態は一切参照・更新しない。**`camera/levelController.ts` の `LevelData` / `LevelControllerState` には `axisMode` を一切持たせていない**。理由: `axisMode` は表示専用でレベル切替・LOD判定のいずれにも影響しないため、これらを管理する状態機械(`LevelControllerState`)に混ぜるとレベル切替ロジックと無関係な値が状態遷移の対象に含まれてしまい、責務が曖昧になるためである。
- レベル名は専用のデータ構造を持たない。Mermaid frontmatterの `title:` を `extractMermaidTitle` で読み取り、`appendMermaidTitleElement` がキャンバス上のテキスト要素として描く(Issue #3で実装済みの経路をそのまま流用)。`%%L1: 名前` 記法を採らなかった理由: 採用するとFR-7.2(マーカーは単独行のみ)の改訂が必要になるうえ、レベル名の置き場所がマーカー行とfrontmatterの2箇所に増え、どちらが正か曖昧になるため。
- `findNamedMarkerLikeLines` が報告するのは、**その行が指しているレベルに正規マーカー(`LEVEL_MARKER_PATTERN`)が1行も無い場合だけ**である(FR-7.11)。初版はこの条件が無く、行の見た目だけで判定していたため、Kennyの実文書で誤検知が続出した(実測): 冒頭の凡例 `%% L1=宣言(あるべき姿) / L2=実態` 、説明行 `%% L1とL2は箱を揃えてある`、レベル本文中の `%% L3の凡例: 赤=是正前` がすべて「マーカーとして扱いません」と警告された。いずれもただのコメントで、`%%L1`〜`%%L3` は別行に正しく書かれており何も壊れていない。この警告に意味があるのは「名前を付けたせいでそのレベルが登録されなかった」ときだけなので、登録済みレベルを指す行は見送る。同じ誤検知は `splitMermaidLevels` 側の「マーカーより前の非空行」警告でも起きたため、そちらは `%%` コメント行を対象外にした(FR-7.5)。
- `findNamedMarkerLikeLines` は行の検出だけを行う純関数であり、警告の生成は行わない。警告の生成は `main.ts` の `buildFromSource` が担う。C4モード・Mermaidモードのどちらの経路に落ちても検出できる必要がある(名前付きマーカーだけの文書は `isMermaidModeSource` がfalseになりC4モードに落ちるため)ため、モード分岐(`buildFromSourceInner`)の外側でこの警告を追加している。
- プロファイル(Issue #1)は実装上の仕組みではなく、「軸の意味(`%% MODE:`)+各レベルの名前(frontmatterの `title:`)」という書き方の規約である。`src/samples/views-profile.ts`(組込サンプル「プロファイル例(採用プロセス/ビュー軸)」)がC4以外の題材でこの規約を使った見本であり、コード上の新しい仕組みは追加していない。

## 14. ファイルにリンク(post-v1.0、FR-8)

ローカルの`.txt`ファイルに「リンク」し、外部エディタ(VSCode等)での保存を自動で画面へ反映する任意機能。旧来の `ui/fileIO.ts` は「保存」(ソースの`.txt`ダウンロード)「開く」(その場限りの1回読み込み)の2ボタンを提供していたが、post-v1.0で「保存」ボタンとダウンロード機能自体(`sanitizeFilename`/`saveSourceAsFile`)を廃止し、「開く」ボタンは本機能の「ファイルを選択」ボタンへ一本化した(Kenny指示)。`ui/fileIO.ts`に残るのは`stripFileExtension`(ファイル名からタイトルを作る)と`readFileAsText`(非対応ブラウザ向けフォールバック読み込み)のみで、いずれも本機能から呼ばれる。SVG/PNGエクスポート(FR-6.1/FR-6.2、`ui/exporter.ts`)はこの改訂の対象外で無変更。

本機能の中核は `FileSystemFileHandle`(File System Access API)を介してファイルへの参照を保持し続け、ポーリングで外部からの変更を検知する「片方向の監視」である。既存パイプライン(`parser → model → layout → render`、および§13のMermaidモード経路)には一切手を入れず、エディタへの入力経路(`EditorController.setValue`)にもう1つの入力元を足すだけの位置づけである。

### 14.1 モジュールと責務

| モジュール | 責務 | 備考 |
|---|---|---|
| `ui/fileLink.ts` | File System Access APIのブラウザ対応判定(`isFileLinkSupported`)、ファイル選択(`pickTextFile`)、読み取り権限確認(`ensureReadPermission`)、変更ポーリング(`createFileWatcher`)、**履歴のIndexedDB永続化**(`loadHistory`/`recordHistory`/`removeFromHistory`)、履歴表示用の時刻整形(`formatHistoryTimestamp`) | DOM/ブラウザAPI依存だが、`createFileWatcher`自体はテスト用に`WatchableFileHandle`という構造的型を介した純粋なポーリングロジックとして切り出してあり、vitest(node環境)でフェイクハンドルを使って単体テストできる。履歴の配列組み立ても同様に純関数へ切り出している(§14.6) |
| `ui/editor.ts` の `setReadOnly` | エディタの読み取り専用状態の切り替え | `EditorState.readOnly`と`EditorView.editable`の2つのCompartmentを同時に切り替える(`readOnly`だけではカーソルは表示されるが編集不可という中途半端な見た目になるCodeMirror 6の既知の挙動への対応) |
| `main.ts` の `setupFileLink` | ツールバーのボタン配線と状態遷移の管理(選択ボタン`#pick-file-button`、履歴メニュー`#file-history-select`、リンク解除ボタン`#unlink-file-button`、非対応ブラウザ向けフォールバック`#file-input`、状態表示`#file-link-status`) | `ui/fileLink.ts`のAPIを組み合わせるオーケストレーション層。`ui/fileLink.ts`自体はDOM要素IDを一切知らない |

`setupFileLink`が管理する状態は「未リンク」「リンク中」の2つのみ(ローカル変数`watcher: FileWatcher | null`で表す)。「ファイルを選択」ボタン(`#pick-file-button`)は未リンク/リンク中を問わず常にピッカーを開き、押すたびに新しいファイルへ乗り換えられる(トグルボタンではない)。「リンク解除」ボタン(`#unlink-file-button`)はこれとは独立したボタンで、リンク中だけ表示される。旧設計にあった「主ボタン(トグル)+副ボタン(再リンク)」の2ボタン構成は、副ボタンを「履歴▼」メニュー(`#file-history-select`、最大`FILE_HISTORY_MAX`件)に置き換える形で廃止した。1件しか覚えられなかった旧設計と異なり、複数ファイルを行き来する運用に対応するための変更である。

非対応ブラウザ(File System Access APIを持たない)では、`#pick-file-button`を`disabled`にはせず、クリック時に隠し`<input type="file">`(`#file-input`)をクリックするフォールバック経路に配線する(FR-8.7)。この経路で読み込んだファイルは監視も履歴登録もしない、その場限りの1回読み込みになる。`#file-history-select`は常に空になるため`disabled`にする。

### 14.2 ポーリング方式を選んだ理由

File System Access APIには、ファイルの外部変更をブラウザへpush通知する仕組みが無い(`FileSystemObserver`はこのアプリが対象とするブラウザ範囲では前提にできない)。そのため「外部エディタでの保存を自動で反映する」という要件を満たす手段は、ハンドルの`getFile()`を一定間隔で呼び直し、内容が変わっていないかを能動的に確認するポーリングのみである。間隔は`constants.ts`の`FILE_LINK_POLL_INTERVAL_MS`(1000ms)で一元管理し、「保存してから画面に反映されるまでの体感待ち時間」と「不要なポーリング頻度」の折衷値とした(要件が具体的な上限を定めていないため最も単純な解釈を採用)。タブが非表示の間(`document.visibilityState !== 'visible'`)はポーリングを止め、無駄な`getFile()`呼び出しを避ける。

### 14.3 `lastModified`と`size`の両方を見る理由

変更検知は`lastModified`**または**`size`のいずれかが前回値と異なることで判定する。VSCode等の保存挙動は環境によって、mtimeだけが変わり内容長は変わらない上書き保存(同じ文字数への書き換え)も、逆に内容長だけが実質的な差分の目印になり得るケースもあり、どちらか一方だけを見ると検知漏れが起こり得るためである。`getFile()`の失敗(ファイル削除・移動・権限失効)はウォッチを止めて`onLost`を1回だけ呼ぶ。

### 14.4 IndexedDBのスキーマと履歴1本化

`FileSystemFileHandle`は構造化複製可能なオブジェクトであり、`localStorage`(文字列のみ)には保存できないため、IndexedDB(DB名`mermarium`、version 1、ストア`handles`)に保存する。**履歴機能への刷新にあたり、DB名・バージョン・ストア構成はいずれも変更していない。** 単一ハンドルを1件だけ持っていた旧キー`linkedFile`は廃止し、代わりにキー`fileHistory`へ`FileHistoryEntry[]`(履歴配列)を丸ごと1本のvalueとして`put`する設計にした。`handles`は`keyPath`を持たないキーバリューストアであるため、「1ハンドル1キー」から「配列1本1キー」へ持ち方を変えてもオブジェクトストアのスキーマ変更・`onupgradeneeded`でのマイグレーション処理は一切不要である(バージョンも1のまま据え置いている)。旧キー`linkedFile`に保存されていたデータを`fileHistory`へ移行する処理は書いていない — 本機能はFR-8として実装されて以降まだ外部リリースされておらず、移行すべき既存ユーザーデータが存在しないため(移行コストを払う理由がない)。

DBが開けない・書き込みに失敗する等はすべて「永続化なし」として握りつぶす(IndexedDBはユーザー環境依存のシステム境界であり、永続化は本機能の主目的〈画面への反映〉に対して補助的なベストエフォート機能であるため)。IndexedDBに保存された値の形が壊れている場合に備え、`looksLikeFileHandle`/`looksLikeHistoryEntry`という最小限の型ガードで読み出し時に検証し、壊れた要素だけを読み飛ばす(1件の破損で履歴全体を失わせない)。

ブラウザの権限モデル上、`FileSystemFileHandle`を永続化できても、そのハンドルの読み取り許可(`queryPermission`/`requestPermission`)はページを再読み込みすると失効し、再許可にはユーザー操作(クリック等)を伴う文脈が必要になる。そのため起動時に`loadHistory()`で前回までの履歴を復元できても、自動では読みに行かず、「履歴▼」メニューとして提示してユーザーのクリックを待つ(`ensureReadPermission`はメニュー選択のハンドラの中で呼ばれる)。

### 14.5 リンク解除と消失(`onLost`)の非対称

「リンク解除」ボタン(`#unlink-file-button`)は`removeFromHistory()`を呼ばない。次回同じファイルへ履歴から1クリックで戻れるようにするための仕様(FR-8.5)であり、「解除」は監視を止めるだけの正常な一時停止として扱う。一方、ウォッチャーが`onLost`(ファイルが見つからない・読み込めない)を報告した場合は`removeFromHistory()`を呼び、そのファイルを履歴からも取り除いた上で完全な初期状態(監視なし、状態表示なし)に戻す。こちらは異常系であり、存在しないファイルへの参照を履歴に持ち越す意味がないためである。同じ非対称は、ピッカーで選んだファイルが直後に読み込めなかった場合(`linkToFile`内、権限確認後の`getFile()`/`text()`失敗)にも適用しており、この場合も`removeFromHistory()`を呼んで履歴を掃除する。

### 14.6 重複判定と履歴組み立ての純関数化

「同じファイルを繰り返しリンクしても履歴に重複登録しない」という要件を満たすため、`recordHistory`は候補ハンドルと既存履歴の各要素を`FileSystemHandle.isSameEntry()`で比較し、一致するインデックス(`findDuplicateIndex`)を求めてから配列を組み立てる。`isSameEntry`はブラウザAPIかつ非同期であり、vitestのnode環境には存在しないため直接テストできない。そこで配列の組み立てそのもの(重複要素を取り除いて新エントリを先頭に積み、`FILE_HISTORY_MAX`件を超えた分を末尾から溢れさせる)は`upsertHistoryEntry(entries, entry, duplicateIndex, max)`という同期の純関数に切り出した。この関数は「重複が既に見つかっている」ことを前提に配列操作だけを行うため、`isSameEntry`にもIndexedDBにも依存せず、vitestで直接ユニットテストできる。`isSameEntry`自体が存在しない・呼び出しが失敗する場合は`isSameEntrySafe`が「別ファイル」側に倒す(誤って別ファイルを同一と判定して履歴から消してしまうより、同名の2件が残る方が実害が小さいという安全側の判断)。

### 14.7 履歴メニューの`<option value>`と、絶対パスを保存・表示できない理由

「履歴▼」の各`<option>`の`value`には、選択されたエントリを特定するための履歴配列のインデックス(`String(index)`)を入れている。`FileSystemFileHandle`はDOM APIのオブジェクトであり文字列化する標準的な方法を持たない(`option[value]`は文字列しか保持できない)ため、`value`自体にハンドルを持たせることはできない。選択時は`history[Number(select.value)]`でその回の`refreshHistoryMenu()`が保持している配列から引き直す設計にしている。

履歴の各エントリ(`FileHistoryEntry`)が持てるのは`name`(ファイル名)と`lastUsedAt`(最終利用時刻)のみで、`D:\Users\...\foo.txt`のようなフルパス・フォルダ構成は保存も表示もできない。これは実装上の手抜きではなくFile System Access API自体の設計上の制約で、`FileSystemFileHandle`はサンドボックス化されたファイル参照であり、そこから絶対パスやディレクトリ構成をJavaScript側へ一切開示しない(ブラウザのセキュリティ設計)。そのため履歴の表示・選択の手がかりはファイル名と最終利用日時に限られる(同名ファイルが複数フォルダにある場合、履歴上は区別が付かない。`FILE_HISTORY_MAX`を10件程度に抑えている理由の一つでもある。`constants.ts`参照)。
